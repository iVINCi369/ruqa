# iroh-bridge

Транспортный сайдкар для второго транспорта Ruqa.

Весь P2P приложения живёт в Bare-воркл ете, а у Bare свой ABI нативных аддонов на
libjs — Node-API он не поддерживает, поэтому npm-пакет `@number0/iroh` (napi-rs)
туда не загрузить. Сайдкар решает это так: iroh крутится в отдельном процессе,
а воркл ет разговаривает с ним по локальному TCP. Одно TCP-соединение = один
QUIC bi-stream, поэтому на файл приходится свой стрим и файлы не толкаются в
общей очереди.

Хост-процесс (Electron main; на мобильных — нативный модуль) поднимает бинарник
и передаёт порт воркл ету через `TransferOrchestratorOptions.irohBridgePort`.
Порт не задан — приложение работает как раньше, на одном hyperswarm.

## Сборка

```sh
cargo build --release
```

## Запуск

```sh
iroh-bridge --bridge-port 0 [--offline] [--mdns]
```

Первая строка в stdout — `{"ready":true,"bridgePort":N,...}`.

- `--offline` — ни релея, ни DNS/pkarr: только прямой UDP и, если попросили, mDNS.
  Наружу не уходит ни одного пакета.
- `--mdns` — обнаружение в локальной сети (`iroh-mdns-address-lookup`).

## Проверка вдвоём

mDNS и выбор пути тестами не проверить — нужны два живых процесса:

```sh
npm run lan:smoke            # обычный режим
npm run lan:smoke:offline    # без релея и DNS
```

Скрипт поднимает два сайдкара, ждёт взаимного обнаружения, гоняет приглашение
с согласием и с отказом и проверяет, что тип выбранного пути приезжает
событием `conn-type`.

## Протокол моста

TCP на 127.0.0.1, первая строка от клиента — JSON, ответ — одна строка
`{"ok":true,...}`, дальше сырой двунаправленный поток:

| операция                                                       | смысл                                                                                                               |
| -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| `{"op":"control"}`                                             | канал событий: `peer`, `stream`, `error`, `closed`                                                                  |
| `{"op":"join","topic":hex,"role":"host"}`                      | начать хостить join-код                                                                                             |
| `{"op":"join","topic":hex,"role":"guest","addrs":["ip:port"]}` | подключиться; `addrs` — известные адреса пира (спаренное устройство, тейлнет), с ними соединение встаёт за один RTT |
| `{"op":"leave"}`                                               | закрыть Endpoint                                                                                                    |
| `{"op":"open"}`                                                | открыть новый bi-stream к пиру                                                                                      |
| `{"op":"attach","id":N}`                                       | принять входящий bi-stream N                                                                                        |

Событие `conn-type` кроме `connectionType` (`relay` | `direct`) несёт `remoteAddr`
выбранного пути и `rttMs`: по одному слову «direct» не отличить честную пробивку
NAT от пути через тейлнет или локальную сеть.

Событие `peer` несёт `binding` — экспортированный keying material соединения,
аналог `handshakeHash` у Noise-сокета hyperswarm, используется для привязки
канала при спаривании устройств.

## Чего здесь пока нет

Join-код напрямую становится секретным ключом хоста, поэтому гость выводит его
EndpointId из кода без обмена. В продакшене так нельзя: владелец кода может
представиться хостом. Нужен HKDF от кода плюс `topic-auth`, который в
репозитории уже есть.

## Проверка между двумя машинами

`tools/nat-probe.py` гоняет сайдкар без приложения: поднимает мост, делает join
и шлёт данные одним bi-stream'ом, печатая все события с таймингом. Хост на
одной машине, гость на другой, topic одинаковый:

```sh
python3 tools/nat-probe.py --bin ./iroh-bridge --role host  --topic <64 hex>
python3 tools/nat-probe.py --bin ./iroh-bridge --role guest --topic <64 hex> --mb 32
```

Если обе машины в одном тейлнете, «direct» будет через него — на время теста
режь UDP на `tailscale0` (`iptables -I INPUT -i tailscale0 -p udp -j DROP`,
то же для OUTPUT) и смотри `remoteAddr`.
